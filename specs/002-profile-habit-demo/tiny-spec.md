## Outcome and scope

Help a Spanish-speaking demo user maintain a sports habit through a coherent profile, a locally saved starting preference and guilt-free scripted support. There is **one evolving person**, not three people with switchable isolated histories. Main home remains a clean sport-entry surface; profile owns preferences, progress and scenario controls.

Included: top-right circular avatar entry patterned on the [v2 mockup](../../docs/mockup_ba_en_movimiento_v2.html); a separate profile surface; first-use onboarding and editing; Mi camino, Desafíos and achievements accessible from profile rather than global home controls; four explicitly simulated same-person scenarios; in-app phone-notification representations; structured notification-to-chat flows ending in existing sport/class/solo surfaces; compatible local storage and focused regression checks. Reuse existing sports, classes, plans, illustrations, safety and fictional-service disclaimers.

Excluded: backend, authentication, new persistent database, real AI/provider/network integration, push/browser notification permission, real booking, attendance detection, geolocation, real elapsed-time scenario triggers, automatic habit transitions, deployment operations, dependency upgrades and unrelated changes. Future automatic habit evolution is explanatory demo narrative only. **No “Otra cosa”, free-text field, pretend comprehension or AI handoff.**

## Settled behavior

### Actual today and profile

- Remove the current global profile dropdown and global Mi camino/Desafíos/achievement controls from main home. A circular avatar at the top right opens a distinct profile route with a Spanish accessible name and keyboard operability. Home/back navigation remains understandable.
- First use without a saved onboarding answer requires choosing exactly one situation: currently not training and wants to start; trained before and returning; already trains. Do not infer an answer from a fixture, old hash or old selected profile. Save the answer locally and display/edit it in profile; after reload, a completed answer is not asked again. Denied storage supports warned in-tab use without promising persistence.
- Changes affect present recommendations/welcome/plan selection, not person identity, prior completions, interests or lifetime achievements. Rest and preference changes never erase history or switch to another person's ledger. No automatic preference change occurs from dates, notifications, completion counts or inactivity.
- Mi camino, Desafíos and achievements describe the same actual ledger with existing Spanish labels and seed/user-simulated origin honesty. There are no independent persisted point/badge counters. Current-period progress may change with real dates; lifetime earned progress does not disappear merely because of a break.

### Four same-person simulations

Profile has four clearly labeled scenario buttons: sustained training; returning after training then a break; stopped training/stopped using the app and receives a reengagement notification; intended to attend a class but missed it and receives a notification. All are views of the **same person** at different demo moments, never persona selectors.

Each scenario exposes its home perspective and a visible simulation label plus **return-to-today** action. Scenario presentation/history examples are ephemeral and clearly distinguished from actual saved history. Selecting, navigating, reloading or leaving a simulation must not write onboarding preference, actual history, achievements or interests. Returning to today restores current real preference and actual ledger, with no simulated progress retained. A direct or stale simulation hash cannot create evidence of a missed class or attendance.

Notification scenarios enter an **in-app simulated phone-notification view** selected from profile. Tapping that notification opens its structured chat, **not home**. Both can subsequently preview the scenario's home perspective and return to today. No operating-system permission, real push event, elapsed-time scheduler or booking/attendance inference is involved.

### Scripted support chat

Notification chats use selectable answers and deterministic tailored follow-ups. Visible Spanish copy explains that a real product would use AI for nuance, while this demo uses scripted answers and implements no AI. Support is respectful, optional and without blame, penalties or achievement removal.

The missed-class chat asks why the intended class was missed, offers the following predefined cases and permits skipping without explanation:

| Answer meaning | Required tailored response and concrete destination |
| --- | --- |
| Something came up | Acknowledge interruption; offer going next time via a relevant existing fictional class surface. |
| Schedule/location inconvenient | Offer alternatives in the existing class catalog/detail surfaces; no location lookup. |
| Disliked activity | Offer choosing another sport/activity through existing sport choice and class/solo paths. |
| Uncomfortable with instructor/class | Offer another group/instructor/activity or solo practice using existing fictional alternatives and solo surfaces. Do not invent confirmed instructor availability. |
| Skip explanation | Acknowledge that no explanation is required and offer a concrete class or solo next step. |

Every branch ends with a usable action, not just reassuring text or a dead end. No branch requires text entry. Inactivity chat gently supports returning without assuming why the person stopped; use predefined choices for an available return action (class or solo), plus skip, with corresponding scripted follow-ups and a concrete destination. No extra reason taxonomy or open-ended intake is required.

Chat and scenario exploration never record completion, attendance, booking or interest. To take an existing action that changes durable demo state, explicitly leave simulation for today's guarded sport/class/solo surface first; state-changing actions cannot silently operate in a preview. Existing destinations retain fictional/no-real-booking notices. Returning to today is always available, including before answering.

### Bounded implementation shape and data compatibility

Use a single actual preference and single canonical actual-history/interest collection in the versioned local envelope; keep the three existing IDs only as content/plan recommendation categories and legacy provenance where useful. Update helpers/selectors/session consumers so completion is attributed to the one person independent of the chosen template. Keep preview scenario and chat step state ephemeral; a route may describe a simulation, but cannot mutate actual storage. Guard preview routes and unsupported IDs with safe navigation and preserve current session abandonment and cleared water affirmations on incompatible navigation.

Legacy valid schema-1 migration must be deterministic, lossless and idempotent. Preserve the original legacy payload/provenance within the migrated envelope, normalize all distinct historical records/completions/interests into the one person's ledger, and preserve snapshots of retired plan/class names and IDs. Distinct legacy records sharing an ID across former profiles must not overwrite each other: qualify their migrated identity by original profile/provenance while keeping original identity available; do not count the same stored completion twice on repeated load. Retain seed origins as illustrative seeds, never relabel them as observed activity. Do not drop another former profile's history merely because it was not selected. Legacy selectedProfileId is not proof of completed onboarding; migration marks the new answer unanswered until explicitly chosen. Fresh storage likewise starts unanswered, with scenario fixtures reserved for preview rather than an automatically selected actual persona.

Keep storage scoped to the existing namespaced demo key; do not clear other localStorage keys. Validate migration output before replacing stored data. If a write is denied, retain usable in-tab state and warning, not a persistence success claim. Invalid JSON, unsupported versions or invalid records retain the current recovery/warning behavior without automatically overwriting the invalid bytes. Deliberate confirmed reset is the existing destructive recovery boundary, affecting only this key and returning to first-use onboarding. Preserve valid legacy data on migration failure; never hide failure behind a clean fixture reset. Old code does not understand the new envelope, so code rollback alone is **not** data rollback: retain original legacy payload for an explicitly authorized restoration, and never automatically downgrade or discard new history.

Sequence contract producers before relying consumers: content types/validator/data references and canonical-state/migration/navigation helpers must agree before onboarding/profile/scenario/chat UI consumes them. Actual-helper migration and preview-nonmutation acceptance gates downstream reliance. This is a dependency constraint, not an implementation task list.
