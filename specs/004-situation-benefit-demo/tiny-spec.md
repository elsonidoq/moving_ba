## Outcome, provenance and scope

The owner wants a convincing Spanish presentation of a person in the selected sport-practice situation: choosing regular practice should show more illustrative benefit progress than starting, while completing a real app practice still advances that presentation. Home should foreground **one** relevant benefit and link to all benefits. Preserve the current photographic/yellow visual style and honest nonredeemability.

Authoritative inputs: the owner decisions supplied to this producer; [constitution](../../.specify/memory/constitution.md); [002 FR-008/009/011/015](../002-profile-habit-demo/spec.md); inspected implementation and [architecture](../../docs/architecture.md), especially “Actual custody and projections”; [content contract](../../docs/CONTENT_CONFIGURATION.md). This owner direction supersedes 002 FR-008 and 003 AC-02 only insofar as they require the displayed benefit-point total to equal actual earned points. It does **not** permit manufactured durable records, independent saved counters, people/accounts, synthetic dates/activities or changes to actual credit rules. Other inherited behavior remains intact.

Included: Home benefit summary; situation-sensitive illustrative **points** on Home/Profile/Benefits; truthful source breakdown and contextual labels; Profile edit integration; separate existing ephemeral previews; minimum Journey copy alignment so its actual point total is not mistaken for illustrative points. Excluded: synthetic session/week/chart/challenge/badge progress, new reward thresholds, redemption/booking/service integration, backend/schema/migration, new people, scenario types, assets, libraries, broad redesign, deployment/push, and unrelated open issues OI-1/OI-2.

## Deterministic presentation contract

### Actual saved journey versus illustration

- `earnedPoints` remains the existing lifetime result from unique eligible saved journey records times `rules.pointsPerCompletion` (currently 10). Preserve legacy seed provenance and existing lifetime inclusion semantics: do not silently drop imported records or reinterpret the formula as counting only newly created completions.
- `illustrativeBaseline` is the selected confirmed situation's configured example-history length times the same points-per-completion. Resolve by `profiles[].scenarioId` to `scenarios.profiles[].id`, not array position. Current fixtures give first=0, returning=20, regular=40. This is a **read-only example source**, not a seed/import operation. Existing validated references suffice; no new configurable point field is necessary.
- `displayPoints = illustrativeBaseline + earnedPoints` in actual mode, derived on demand, never persisted. The situation is a recommendation/presentation preference for the **same person**. Editing it changes the baseline immediately after confirmation, not the earned component. Returning to a previous situation recomputes the same baseline plus all earned points, not a separate saved balance. Cancelling does nothing. Reload preserves the confirmed situation and saved journey and recomputes presentation.
- Actual sessions, active weeks, weekly goal count, activity bars, history, challenges and badges remain derived from actual records exactly as before. Weekly goal target may still follow the situation's existing configured target. Do not make activity look regular by inventing those counts. The requested illustrative progression is the explicitly labeled benefit-point presentation; the actual activity panels remain explicitly saved-journey data.
- Home summary, Profile illustrative points and Benefits hero/card eligibility use the same mode-aware presentation result. Profile retains actual sessions/weeks/chart, and shows earned points in the breakdown rather than silently replacing their meaning. Journey remains the saved-record view: label its points `Puntos de tu recorrido guardado` and distinguish it from illustrative benefit progress. No illustration enters history rows, dates or earned badge/challenge calculations.

### Truthful Spanish labels

Keep concise contextual honesty, not a revived blanket footer. Runtime-configurable visible and accessible copy must identify the situation and explain the split on each actual Home/Profile/Benefits surface. Suitable wording (equivalent clear Spanish is acceptable): `Progreso ilustrativo · {situation}`, `Puntos ilustrativos`, `Base de ejemplo: {baseline} puntos`, `Puntos de tu recorrido guardado: {earned}`, and `La base cambia según la situación elegida; tus prácticas guardadas se conservan y suman puntos.` Profile edit instructions must no longer imply that selection changes recommendations only: it also changes the illustrative base, never saved history. Label activity sections `Tu recorrido guardado` where needed to prevent mixed-metric inference. Avoid invented achievements, identity, verified physical activity or the assertion that example points were earned.

Retain the existing local nonredeemability message and show a concise qualification by the Home card and full benefit list: e.g. `Beneficios ilustrativos, sin canje ni ofertas confirmadas.` `Meta alcanzada` means illustrative threshold met, never an issued ticket, available offer or entitlement. No redemption action, partner guarantee or official affiliation.

### Home selection and all-benefits view

From validated configured benefits and the current mode's display points:
1. If any threshold is <= points, choose the highest such threshold.
2. Otherwise choose the lowest threshold (nearest upcoming threshold).
3. Equal thresholds use stable ID lexical order as a deterministic repository-derived tie rule, independent of array order.
4. Render exactly one benefit card with its existing local photo/alt, title and description. If below threshold show exact `threshold - points` using Spanish wording such as `Te faltan {count} puntos para esta meta`; at/above show `Meta ilustrativa alcanzada` (zero remaining). Only the visual fill caps; numeric totals never cap.
5. Always provide `Ver todos los beneficios` to the existing guarded Challenges/Benefits destination, preferably its benefits section with a semantic target/focus treatment; no new route system is required. The list retains all configured benefits and uses the same displayed total/eligibility/remaining arithmetic.
6. For an empty benefit collection show no fabricated card, a Spanish empty state such as `No hay beneficios ilustrativos para mostrar`, and retain the all-benefits link to the equally truthful empty list. Current `entities` validation defaults to nonempty: permit an empty benefits array specifically, without weakening validation of nonempty entries or other collections.

Current examples: with no saved records, first 0 selects coffee/30 with 30 remaining; returning 20 selects coffee with 10 remaining; regular 40 selects coffee as highest eligible, not the upcoming garden/60. At 60 select garden; at 90 or above select yoga. Completing one practice from returning 20 reaches 30 and changes coffee to reached; from regular 40 reaches 50 without claiming the garden is eligible.

### Preview semantics

Existing explicit Profile scenarios remain ephemeral, separate, labeled `Escenario simulado` with selected name and `Volver a hoy`. In preview use **only** `selectPreviewJourney`'s configured scenario projection/reference date: display points equal that projection's points, with no additional situation baseline and no actual earned points. Its existing sessions/challenges/badges/chart remain scenario-only. Label points `Puntos del escenario` and identify them as an example; do not show an actual earned breakdown inside preview. Home card and Benefits use that same scenario total and selection rule. Never replace a deliberately selected preview scenario with the new actual-mode situation baseline. Hide actual intention as before. Enter/navigate/chat/exit leave actual storage bytes identical; reload/storage event discards preview, returns existing guarded actual flow and recomputes actual presentation. Durable practice/actions remain guarded until explicit exit and separate actual action.
