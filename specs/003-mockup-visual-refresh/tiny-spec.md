## Context, provenance and precedence

The owner wants the existing Spanish browser app to recover the photographic mockup's more beautiful presentation: compact cards, plentiful meaningful glyphs/icons, clear hierarchy and a richer profile, while keeping the yellow brand. This is a small presentation/entry-flow correction, not a new product architecture.

Authoritative inputs are the current owner direction retained in the planning session, the [constitution](../../.specify/memory/constitution.md), and this bounded source. The [photographic reference](../../docs/mockup_ba_te_mueve/index.html) is visual evidence, not an operational contract. In that file, lines 36–37 define `pageWelcome`/`pageOnboarding`, line 46 `pageProfile`, lines 48–49 `pageNotice`/`pageChat`; CSS lines 6–10 and card/navigation helpers lines 28–35 supply visual vocabulary. Compare rendered reference and app, not just screenshots of code.

The owner explicitly supersedes only contrary UI requirements in [002 specification](../002-profile-habit-demo/spec.md) FR-001/002/009/010: no-welcome, no-lock-screen-look and mandatory disclaimer prose. This permits the requested welcome, notification-inspired presentation and removal of repetitive disclaimer-like copy. It does **not** supersede state custody, safe practice, preview isolation, guarded routes, real-service prohibitions or constitution honesty. Other inherited behavior stays intact; any inherited requirement to use literal `demo` in UI is fulfilled instead by contextual Spanish example/scenario wording under this new owner direction, not by removing the underlying limitation.

## Scope and settled constraints

Included:
- Welcome followed by situation selection for unchosen users; richer profile/edit cards; mockup-inspired notice then scripted chat for both manually selected notice scenarios.
- Common yellow-accent hierarchy, compact surfaces, purposeful icons, spacing and typography on these surfaces and bounded visual convergence of the other two scenario home views and their existing destinations.
- Remove **all in-app `demo`/`demostración` wording and disclaimer-like presentation**, including header boilerplate, duplicated notice/chat paragraphs and the entire three-paragraph footer. Remove these exact footer paragraphs rather than shortening or relocating them wholesale:
  1. `Prácticas ilustrativas: esta demo no verifica actividad física ni da indicaciones personales. No hagas ejercicios con dolor.`
  2. `Antes de entrenar de verdad, estas propuestas requieren revisión de una persona profesional calificada y adaptación a tus necesidades.`
  3. `Propuesta conceptual, no es un servicio oficial de GCBA ni tiene patrocinio confirmado.`
- Preserve useful, actionable exercise safety at the plan/exercise decision point, not in a repeated footer. Keep meaningful storage failure/reset warnings and concise transaction-specific limitations.

Excluded: backend/database/persisted schema changes, migrations, dependency or lockfile changes, new icon library, remote fonts/photos or asset acquisition, real push/browser Notification permissions/service workers, OS impersonation, geolocation, bookings, attendance/absence inference, verified-activity claims, AI/provider calls, free text, new scenario types, invented profile metrics/charts, new reward rules, disposable prototypes, app-wide redesign unrelated to these presentation seams, deployment/live access or push. Existing internal names/storage key containing `demo` need not be renamed; visible and assistive copy must change. No current authority extends to app, tests, docs, assets, dependencies, memory, guidelines or STATE.

Honesty is expressed in context, not a replacement blanket disclaimer:
- Profile entry is explicitly `Explorar situaciones`; scenario context remains visibly marked `Escenario simulado` (with the selected situation name) and offers `Volver a hoy` across preview destinations.
- A notice is an in-app scenario entered by the person. Use a concise contextual cue such as `Situación elegida por vos`; do not imply delivery, live push or observed inactivity/absence. Notification-inspired image/translucent card is allowed; no fake OS status bars, device chrome, system permission prompt, real-time delivery assertion or lock interaction. A decorative reference clock is unnecessary and must not appear as current device time.
- Chat can say `Elegí una respuesta` / `Respuestas predefinidas`; remove repeated scripted/future-AI disclaimers and future-AI promotion rather than replacing them with a false live assistant claim.
- Class/interest/intention, fictional locations/prices and illustrative benefits retain short local cues (`Clase de ejemplo`, `Intención guardada`, `No reserva un lugar`, `Ubicación de referencia`, `Sin canje`, as applicable). Do not advertise actual offerings, official GCBA affiliation or confirmed partners. No official `Buenos Aires Ciudad` logo is adopted.
- Reset/recovery copy describes this person's local data accurately, not three reset profiles. Invalid/denied storage feedback remains truthful, including tab-only behavior and old data possibly returning on reload.

Welcome behavior is deterministic: invalid storage recovery takes priority; after confirmed successful or tab-only reset, show welcome; cancellation is a complete no-op. Welcome/back-to-welcome never chooses a situation. Situation selection remains unselected until explicit user interaction and `Continuar` remains disabled until a choice. Confirmed persisted preference bypasses both stages on reload/deep-link entry and retains existing valid destination guarding. No state redesign or migration is needed. Keep the single command owner as durable authority. If landing/reset integration requires a tiny transient entry-stage signal, keep it memory-only and preserve storage-event invalidation/recovery precedence. Situation edit only changes preference. Enter/answer/exit preview do not write. Preview controls remain independently command-guarded, not just cosmetically disabled.

Rollback is the focused implementation diff, not data restoration: no persisted representation changes are allowed. Stop/replan if implementation appears to require migration, new dependencies or weaker guards. Preserve existing missing-image/config/storage error behavior; do not broaden into unrelated fixes.
